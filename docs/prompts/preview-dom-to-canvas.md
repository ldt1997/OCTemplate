## 预览与导出画布实现方案

新模板继续沿用当前 `akRecruit` 的模块分工与 toolbar 配置方式，不新增复杂架构，只调整预览与导出的实现方式：

- 预览从当前 DOM 结构映射改为 `canvas` 渲染
- 导出继续使用 `canvas` 重绘
- 预览与导出共享同一套模板尺寸、视觉 spec 和布局计算
- 是否支持图片拖动与缩放，该能力由模板自行决定

### 一、适用范围

该方案适用于所有新模板，并遵守以下原则：

- toolbar 配置方式保持不变
- 页面级状态组织方式保持不变
- 模板画布尺寸不写死，由用户决定
- 预览与导出必须尽量一致
- 导出结果不能受屏幕尺寸、预览缩放和设备像素比影响
- 不引入额外重型库

### 二、文件职责保持不变

新增模板时，仍沿用现有文件分工：

- `xxxPage.tsx`
  - 负责页面编排、导出按钮、组合 Toolbar 与 Preview

- `useXxxEditor.ts`
  - 负责表单状态、图片上传、Object URL 生命周期、异步副作用、导出 handler

- `xxxConfig.ts`
  - 负责模板尺寸定义、默认表单值、资源映射、模板级视觉 spec

- `xxxLayout.ts`
  - 负责预览与导出共享的纯布局计算
  - 包含文本换行、位置计算、尺寸计算、图片绘制参数计算

- `xxxPreview.tsx`
  - 负责预览 `canvas` 渲染
  - 如模板支持图片交互，则负责绑定交互并回写表单状态

- `xxxPoster.ts`
  - 负责导出 `canvas` 重绘
  - 负责导出资源加载与导出入口

### 三、模板尺寸定义

每个模板必须在 `xxxConfig.ts` 中显式提供自己的画布尺寸定义。

要求：
- 预览与导出共同消费同一份尺寸定义
- 所有布局计算都基于这套模板尺寸进行

### 四、预览实现方式

`xxxPreview.tsx` 不再使用 DOM 拼装最终画面，而是只渲染一个预览 `canvas`。

要求：

- 预览容器可以继续沿用现有页面结构
- 预览画布显示尺寸可随容器缩放
- 预览内部绘制始终基于模板设计尺寸进行坐标映射
- 影响最终图片结果的元素，必须通过 `canvas` 绘制，而不是依赖 DOM 样式模拟

预览的职责是：

- 消费 `form + config + layout`
- 根据当前模板尺寸绘制预览画面
- 在支持交互的模板中，把交互结果回写统一表单状态

### 五、导出实现方式

`xxxPoster.ts` 继续负责导出，但必须与预览共享同一套绘制依据。

要求：

- 导出时创建独立 canvas
- 导出尺寸严格使用模板定义尺寸
- 不允许通过截图预览区域导出
- 不允许依赖 DOM 样式保证一致性
- 导出应基于共享 spec 与共享 layout 重新绘制

### 六、预览与导出共享内容

为保证一致性，预览与导出至少应共享以下内容：

- 模板尺寸定义
- 模板级视觉 spec
- 文本换行逻辑
- 位置与间距计算
- 图片绘制区域计算
- 颜色、字体、字号、描边等视觉参数

允许预览与导出在以下方面不同：

- 预览使用轻量资源或降采样资源
- 导出使用原始资源或高质量资源
- 预览优先交互流畅
- 导出优先结果质量

### 七、图片交互能力

用户拖动、缩放图片属于可选能力，不是所有模板都必须支持。

要求：

- 是否支持图片交互，由模板决定
- 支持交互的模板，可继续沿用现有图片交互 hook
- 交互结果应统一回写表单状态，如 `imageScale`、`imageOffsetX`、`imageOffsetY`
- 不支持交互的模板，不需要引入额外交互逻辑

本方案默认只覆盖：

- 图片平移
- 图片缩放

如模板需要旋转、裁切或更复杂交互，应由该模板单独扩展，不作为新模板默认要求。

### 八、性能要求

新模板的画布方案应遵守以下性能原则：

- 预览与导出使用不同渲染链路
- 预览优先保证流畅，不要求直接使用导出级资源
- 导出时再使用高质量资源重绘
- 图片交互过程中只更新变换参数，不重新生成图片内容
- 替换上传图片时，必须回收旧的 `ObjectURL`
- 页面卸载时，必须清理当前图片 `ObjectURL`
- 导出优先使用 `canvas.toBlob()`，避免默认使用 `toDataURL()`

如果模板包含用户上传图片，建议：

- 预览阶段使用更适合编辑的资源
- 导出阶段使用原始资源重绘

### 九、兼容性要求

该方案需同时支持浏览器端和移动端访问。

要求：

- 使用同一套模板尺寸与坐标逻辑
- 预览缩放不影响导出结果
- 交互能力需适配触屏场景时，应优先保证基础可用
- 不依赖不稳定或不可控的 DOM 渲染结果作为导出依据

### 十、实现边界

为控制复杂度，新模板默认按以下边界实现：

- 只改造预览与导出画布部分
- toolbar 配置结构不改
- 页面状态分工不改
- 不额外引入通用 scene engine
- 不预先抽象多图层编辑系统
- 不要求所有模板都支持图片交互

如果某个模板本身只有静态内容或仅有文本展示，也应仍然走统一的 `canvas` 预览 + `canvas` 导出方案，以保证实现方式一致。
